# VISION — Product & Engineering

The durable north star: what is true about the product and its architecture. *How we work*
lives in [CLAUDE.md](../CLAUDE.md); *what to build* in
[REQUIREMENTS.md](REQUIREMENTS.md); *when* in [ROADMAP.md](ROADMAP.md).

Living but slow-moving. Change it only when a genuine principle changes, and record the reason
in an [ADR](decisions/).

---

## 1. Product

A native macOS Markdown editor—pure and simple.

**Pitch:** *The Markdown editor that feels like it came with macOS.*

The product edits ordinary files rather than creating a library, workspace, account, or private
document format.

## 2. Objectives

In priority order:

1. **Trustworthy files.** A document remains an ordinary `.md` file that other tools can open.
2. **Interoperable output.** Text generated by the app follows a named, testable Markdown
   specification instead of an undocumented house dialect.
3. **No surprises.** Standard macOS document and editing behavior should work as expected.
4. **Local and private.** Core editing is offline, account-free, and telemetry-free.
5. **Safe companion files.** Adding an image must not overwrite, move, alter, or delete the
   source image or unrelated files.
6. **Fast and light.** Native performance and a small dependency and memory footprint.

When objectives conflict, preservation and non-destructive behavior outrank convenience;
standards-based source outranks renderer-specific decoration.

## 3. Product principles

- **The file is the truth.** No database, hidden identifier, base64 payload, or private metadata
  is required to understand a document.
- **Preserve unfamiliar source.** The editor may not understand every extension a file contains,
  but it must leave unknown text alone.
- **Be precise about compatibility.** Standard Markdown syntax does not imply that every renderer
  can display every referenced media format. In particular, HEIC/HEIF is native on Apple
  platforms but not universally rendered elsewhere.
- **Prefer reversible behavior.** A failed operation may leave a recoverable unreferenced file,
  but must not leave a newly broken reference or destroy existing data.
- **Ride the platform.** Prefer macOS document, text, accessibility, spelling, undo, drag, and
  paste behavior where it satisfies the requirements.

## 4. Editing model

- The target is two views over the same source: **WYSIWYG** (eventual default) and
  **live-styled source**, toggleable without rewriting the document.
- Source mode displays the actual Markdown. An image remains `![]()` source; rendering it inline
  belongs to WYSIWYG.
- Live styling is presentation, not parsing or normalization. It never changes saved text.
- Unknown and unsupported syntax remains editable and round-trips unchanged.
- The delivery sequence is plain text → live-styled source → WYSIWYG default.

## 5. Markdown compatibility contract

### Supported source dialect

The MVP dialect is:

- **CommonMark 0.31.2** for core Markdown; and
- the **formal GitHub Flavored Markdown 0.29-gfm specification** for tables, task-list items,
  strikethrough, and autolinks.

“GFM” means the published specification, not every additional feature rendered on github.com.
The app does not claim parser conformance merely because its source highlighter recognizes a
token. Generated Markdown must pass focused conformance fixtures derived from those named specs.

Footnotes, `==highlight==`, superscript, subscript, definition lists, emoji shortcodes, heading
attributes, and smart-typography transformations are not part of the MVP dialect. They may be
considered later as explicit, named **dialect profiles** with compatibility documentation.
Until then, such text is preserved but is not presented as supported semantics. This is
especially important for `~text~`: formal GFM treats one or two tildes as strikethrough, so it
cannot simultaneously mean subscript.

Fenced code blocks receive a source-level monospace treatment. Language-aware coloring inside
fences remains deferred until a code-highlighting engine is selected.

### Images and companion assets

Users add images by pasting or dragging them into a saved document. There is no separate
“Import” document command.

- The app copies added image files into a visible `assets/` directory beside the Markdown file
  and inserts a standard relative image reference such as `![](assets/diagram.png)`.
- The directory is a shared destination, not an app-owned store. The app may reuse it but never
  assumes ownership of pre-existing contents.
- PNG, JPEG, GIF, HEIC, and HEIF files are copied byte-for-byte. HEIC/HEIF is never silently
  converted to JPEG or another format.
- Bitmap-only clipboard data is encoded as PNG because no original file representation exists.
- The source file remains untouched. References are inserted only after destination files exist.
- The app generates portable ASCII filenames and never overwrites a different existing file.
- Image descriptions initially remain empty rather than using a filename as fake alternative
  text. The editor makes the description easy to fill in.
- The app emits no image dimensions, raw HTML, title, base64 data, or private metadata.
- Undo removes inserted Markdown only; it does not delete an asset. Deleting a reference likewise
  does not delete a file.
- Save As, rename, or moving a loose Markdown file does not silently move or duplicate its
  companion assets. Relative-path semantics remain ordinary and visible.

## 6. Non-goals

- No notes library, graph, backlink index, or knowledge-base behavior.
- No proprietary sync or collaboration service.
- No account or telemetry.
- No cross-platform application; the files remain cross-tool.
- No claim that loose `.md` plus `assets/` is an atomic document package.
- No automatic asset garbage collection.
- No remote-image downloading.
- Mermaid, YAML front matter, wiki-links, transclusion, tags, image sizing extensions, and
  dialect profiles are post-MVP possibilities, not current commitments.

## 7. Engineering decisions

- Pure Swift and SwiftUI-first; use AppKit behind narrow adapters where required.
- `DocumentGroup` and `FileDocument` remain the document model
  ([ADR-0006](decisions/0006-document-model-filedocument.md)).
- The editor uses TextKit 1 `NSTextView`
  ([ADR-0008](decisions/0008-textkit1-nstextview-editor-engine.md)).
- Live source styling uses a deliberately lexical compiled-regex highlighter
  ([ADR-0009](decisions/0009-regex-live-highlighting-engine.md)).
- Added-image placement follows
  [ADR-0011](decisions/0011-image-placement-and-portability.md).
- Third-party dependencies remain unadopted. A structural parser may be selected when WYSIWYG
  work requires one; that decision must name the exact dialect it implements.

## 8. Invariants

Breaking an invariant is a bug. Changing one requires explicit approval and an ADR.

- **INV-1 — No data loss.** Crash, quit, view switching, adding an image, or an I/O failure must
  not destroy document text, source images, or unrelated files.
- **INV-2 — Source fidelity.** Opening and saving without an edit leaves source bytes unchanged,
  modulo an explicitly documented normalization.
- **INV-3 — Ordinary files.** Documents are plain Markdown and visible companion files; no hidden
  database or proprietary package is needed.
- **INV-4 — Offline.** Core editing and image placement make no network request.
- **INV-5 — Native behavior.** Standard macOS shortcuts, menus, accessibility, undo, paste, drag,
  and document lifecycle remain available unless an approved requirement says otherwise.
- **INV-6 — Accessibility.** The app is usable with VoiceOver and full keyboard control; it never
  invents misleading image alternative text.
- **INV-7 — Defined dialect.** Markdown generated by the app is valid CommonMark 0.31.2 plus
  formal GFM 0.29-gfm; unknown source syntax is preserved.
- **INV-8 — Non-destructive assets.** Image placement never overwrites, moves, edits, or deletes
  a source image or a pre-existing destination file.
- **INV-9 — Commit after storage.** The app inserts an image reference only after every file for
  that user action exists at its final destination.
- **INV-10 — Containment.** Generated paths resolve inside the selected sibling `assets/`
  directory; symlinks, aliases, packages, and hostile provider filenames cannot escape it.

## 9. Evaluation criteria

Designs are rejected if they fail source preservation, standards validity, non-destructive file
handling, containment, accessibility, deterministic collision behavior, failure safety, or
automated verification.

Designs that pass those gates are compared by:

1. compatibility across Markdown tools and filesystems;
2. predictable paste, drag, undo, Save As, and failure behavior;
3. minimal prompts and configuration;
4. implementation and maintenance cost;
5. filename and source readability;
6. privacy and metadata consequences;
7. performance and concurrency safety; and
8. ability to add explicit dialect or asset workflows later without migration.

## 10. Distribution

- Direct download, signed with a Developer ID and notarized by Apple.
- Not sandboxed for now, avoiding sibling-file access friction during development. App Sandbox
  remains a future distribution decision.
