# 0011. No Mac, not even once: the update key comes from a secret, and signing is ad hoc

- Status: accepted; its optional `CERTIFICATE_P12` path was retired by [0015](0015-no-apple-developer-account-releases-are-ad-hoc-for-good.md)
- Date: 2026-11-26

## Context and problem

Releasing must need nothing from the maintainer's Mac. The first release design had a one-time `Scripts/release-setup.sh` run on the Mac, copied from sibling projects that export their certificate and update key from a keychain; the maintainer rejected it, because the repository is supposed to work without the Mac.

## Decision drivers

**Criteria.**

1. No step on the Mac, ever.
2. Updates keep working for every installed copy.
3. Security: no key in the repository, in logs, or in a session's transcript.
4. One obvious path, cost.

## Considered options

**Alternatives, ranked.**

| Option | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| **A. Key derived from a secret password; ad hoc signing (chosen)** | ✓ | ✓ Sparkle accepts any identity while the EdDSA key is unchanged | ✓ only the secret holds it | ✓ one secret |
| B. Key generated by a workflow, stored as a secret with a personal access token | ✓ | ✓ | ✗ a token that can write secrets | ✗ a token to create, rotate, and an extra workflow |
| C. Key generated in this cloud session and handed to the maintainer | ✓ | ✓ | ✗ the key passes through a transcript | ✓ |
| D. Certificate created through the App Store Connect API in CI | ✓ | ✓ | ✓ | ✗ needs a paid account and an API key first |
| E. Keep `release-setup.sh` (the siblings' shape) | ✗ | ✓ | ✓ | ✓ |

## Decision

**Decision.** Releasing needs nothing from the maintainer's Mac. `Scripts/release-setup.sh`, a
one-time script run on the Mac, was rejected: the repository is supposed to work without the Mac.
latchkey and Otos both export their certificate and update key
from the Mac's keychain, and Otos repeats that yearly, so copying them was wrong here.

- The EdDSA update key is derived on GitHub's runner from one secret, `SPARKLE_SEED`, a random
  password (`Scripts/sparkle-key.sh`). It was first a GitHub environment secret; its master copy is
  now an Azure Key Vault, which the release job reads keylessly through OIDC
  (`docs/development.md`).
- The build is signed ad hoc unless an optional `CERTIFICATE_P12` is set.
- `Scripts/release-setup.sh` is deleted.

## Consequences

**Where A is worse.**

- **Losing the password breaks updates.** Installed copies reject every later update until
  reinstalled by hand, so it belongs in a password manager.
- **The key is only as strong as the password.** A generated password of 32 or more characters is
  well beyond guessing, but it is not a keychain.
- **Ad hoc signing.** The first open needs "Open Anyway". Each update has a new code identity, so
  macOS may ask again for permissions it granted to the previous build. A Developer ID removes
  both and can be added later without breaking updates (Sparkle 2.10.1 `SUUpdateValidator`: the
  same EdDSA key with any signing identity passes). Until then vision.md's notarized download is
  not met.
- **An ad hoc app cannot load its own frameworks** under the hardened runtime, which cost build 202
  every launch. It now carries the library-validation exception, which a Developer ID build does
  not need ([ADR 0012](0012-an-ad-hoc-app-needs-the-library-validation-exception-and-a.md)).

## Confirmation

`Scripts/test-release-scripts.sh` (run by the gate) proves the key derivation and signature checks; every release runs Sparkle's `sign_update --verify` before publishing.

**Proof.**

- `Scripts/test-release-scripts.sh`:
  - the same password gives the same key, and a different one a different key;
  - a signature verifies under Python's `cryptography`, an implementation independent of the
    OpenSSL that made it;
  - a changed file fails to verify;
  - mutations of the derivation and of the signed input turn it red.
- Every release also checks its signature with Sparkle's own `sign_update --verify` before
  publishing.
- Observed since: v1.0.0 (build 202) published and installed, and it could not start at all — the
  signing above was published unlaunched ([ADR 0012](0012-an-ad-hoc-app-needs-the-library-validation-exception-and-a.md)).
- Not yet observed: an update installing on a real Mac.

## Retirement proof

A Developer ID and update key held somewhere that needs no Mac step, which would allow a keychain-held key instead of a derived one.

## Reversal plan

Generate a conventional EdDSA key, keep it in the vault, and ship an update signed by both keys during the switch; losing the old key strands installed copies.
