# REQUIREMENTS

The authoritative current behavior contract: what the app does, what is under correction, and
how delivered behavior is verified. Current architecture is in
[ENGINEERING.md](ENGINEERING.md).

## Conventions

- **ID:** `REQ-###`, assigned sequentially, never reused.
- **EARS notation** — UPPER-CASE keywords: `WHEN` (event), `WHILE` (state), `IF…THEN`
  (unwanted), `WHERE` (optional); otherwise a ubiquitous "The system shall …". One "shall"
  per requirement.
- **Status:** `Planned` · `Active` · `Done` · `Correction` · `Deferred`. `Correction` means the
  current implementation is known not to satisfy the current requirement completely. Move a row
  to `Correction` in the same change that reproduces a defect against it.
- **Done means observed passing.** A row is `Done` when its cited tests were seen to pass, not
  when its code was written. `—` means not built.
- **Traceability** is a cross-reference for humans, not a schema. Rows name the production types
  and the tests that cover them; `// Verifies: REQ-###` comments in tests point back. Nothing
  enforces this mechanically — see `docs/DECISIONS.md` for why.
- **Verification kinds (no manual or UI tests, ever):** `test` = automated unit/component test
  needing no UI automation · `inherent` = satisfied by construction, either because a standard
  framework provides the behavior (`NSDocument` provides Versions) or because inspection proves
  an absence (makes no network calls) · `visual-review` = one passive screenshot of the app's own
  window, for human oversight of rendering. `visual-review` is never a standalone proof.
- **Liveness:** a requirement promising a capability carries at least one proof that the
  capability succeeds, not only proofs that it refuses. See `CLAUDE.md` §3.
